# 6. Quality assurance

Mathematical correctness is the product. QA has three layers, from cheapest to most
expensive:

1. **Structural checks** (CI, automatic): the site builds; labels, front matter, graph and
   widget configs are valid; spelling.
2. **Computational verification** (CI, automatic once written): every computation on a page,
   from worked examples to exercise answers to widget numbers, is re-done by SymPy and must
   agree.
3. **Proof and pedagogy review** (human + AI reviewer, checklist): what code can't check.

A page's **status** records how far it has got through these layers (§6.6).

## 6.1 Computational verification with SymPy

### Layout

```
verify/
├── conftest.py                 # loads verify/_answers.json (refuses a missing or stale one), registers the coverage plugin
├── mathcheck/
│   ├── __init__.py             # covers(), answer(), the canonical symbols (x, t, n, …), limit_is() and the other helpers
│   ├── latex.py                # parse_answer(): normalise + sympy.parsing.latex (antlr) + post-processing
│   └── equality.py             # equal(), equal_up_to_constant(), equal_on_domain(), numeric_spot_check()
├── _answers.json               # generated by scripts/extract_answers.py (git-ignored)
├── _coverage.json              # written by the coverage plugin during the pytest run (git-ignored)
├── test_mathcheck.py           # tests for the helpers themselves (parser golden cases, the AST fixture)
├── fixtures/                   # answers-ast.json (mystmd's AST of the answer shapes) and make_answers_ast.py
└── calculus/
    └── limits/
        └── test_limit_of_a_function.py
```

### The `@covers` registry and how coverage is counted

Each test declares which labelled block(s) it verifies with `@covers`. A declaration alone
counts for nothing: an author's skeleton of empty `@covers` stubs must not look like
verification. The coverage plugin in `conftest.py` records, **during the pytest run**, which
labels are actually covered:

- a label counts as covered only if a test declaring it **passed**, and no test declaring it
  failed. Skipped, xfailed, xpassed and failed tests count as uncovered;
- an `exr-` label also needs that test to have called `answer(label)`. `mathcheck` records
  each call, so a test that never reads the page's answer can't cover an exercise;
- an `eg-` label also needs the test to have made at least one `mathcheck` assertion (`equal`,
  `limit_is`, …). `mathcheck` counts these per test: a helper call counts when it returns
  True (so `equal(a, b)` without `assert`, returning False, adds nothing);
- the passing test must be in the page's `maths.verify` file, the file the verified badge
  links to (`check_frontmatter.py` checks that this is `verify/<subject>/<chapter>/test_<topic>.py`);
- an exercise whose Answer is `manual` has nothing for `answer()` to read (it raises), so a
  test can't cover it. It counts only through the reviewer's note in `maths.manual_checked`
  (§6.6);
- the result is written to `verify/_coverage.json`. `check_coverage.py` runs after pytest (in
  `npm run verify` and the CI `verify` job), compares it with each page's labels and status
  (§6.6), and prints the coverage that the PR template asks for. It refuses a stale file: one
  written before a page in the toc or a test file under `verify/` last changed. It also fails
  on an `@covers` label that no page has (a typo would leave the real label uncovered).

The author's skeleton therefore uses `pytest.skip("for the verifier")` stubs, which count as
uncovered until the verifier replaces them.

```python
# verify/calculus/limits/test_computing_limits.py
import sympy as sp
from mathcheck import covers, answer, equal, x

@covers("eg-calc-computing-limits-factor")
def test_factor_example():
    # The page computes lim_{x→3} (x^2 - 9)/(x - 3) by factoring; check each displayed step.
    expr = (x**2 - 9) / (x - 3)
    assert equal(sp.factor(x**2 - 9), (x - 3) * (x + 3))      # step 2 on the page
    assert equal(sp.limit(expr, x, 3), 6)                     # boxed result

@covers("exr-calc-computing-limits-conjugate")
def test_conjugate_exercise():
    expected = sp.limit((sp.sqrt(x + 1) - 1) / x, x, 0)
    assert equal(answer("exr-calc-computing-limits-conjugate"), expected)   # the answer *as printed on the page*
```

Always compare with `equal`, never with `==`. `==` is structural in SymPy, so a correct
answer in a different form fails.

### Single source of truth for answers

The answer a student sees is the one that gets checked. There is **no copy** of it in Python.

1. `npm run verify` (locally and in CI) builds the MyST AST (`npm run ast`, i.e.
   `myst build --site`). It takes seconds, but it also fetches the site theme, so it needs
   the pinned theme from [05 §5.5](05-tooling-and-build.md) to be reachable or cached.
2. `scripts/extract_answers.py` walks `content/_build/site/content/*.json`. For each
   `exercise` node, it finds child `admonition` nodes whose class contains `answer`. It reads
   their content in document order and collects one LaTeX string per math span:
   - `inlineMath`/`math` nodes: their `value`;
   - `text` nodes whose whole value is a number (`^[+-]?[0-9.]+$`). mystmd always turns
     number-only inline math such as `$0.69$`, `$6$` or `$-3$` into plain text, so these
     must be read as answers too;
   - `span` nodes that mystmd builds from simple powers and indices such as `$2^{10}$`
     (text plus `superscript`/`subscript`), rebuilt as `2^{10}`.

   It writes `{"exr-…": {"latex": ["\\frac{1}{2}"], "manual": false, "page": "…", "type": "expr", "line": 12}}`,
   plus the sha256 of every page in the toc. mystmd stores each page's source hash in its JSON,
   so an AST older than its page is an error; and `verify/conftest.py` refuses to run when a
   page changed (or entered or left the toc) after the extraction. On any error (no Answer or
   two, an unknown answer class, an Answer without math, math KaTeX rejected, a stale AST) the
   script writes nothing and deletes an existing `_answers.json`. A `bool` answer is the word
   True or False in plain text, read as such.
   The AST shape is `exercise{label} > admonition{class:"dropdown answer"} > paragraph > (inlineMath | text | span)`.
   For multi-part answers `(a) … (b) …`, the order of the list is the order of the parts.
   `test_mathcheck.py` has an AST fixture with a symbolic, a numeric and a `2^{10}` answer,
   so a mystmd upgrade that changes any of these shapes fails one clear test.
3. `answer(label)` in tests parses that LaTeX with `mathcheck.latex.parse_answer`. That
   function:
   1. normalises the input: the project's macros expanded from `content/myst.yml` (so
      `\abs{x}` → `\left\lvert x \right\rvert`); `\dfrac`→`\frac`; `\left`/`\right`, `\,` and
      the other spacing dropped; `\lvert`/`\rvert` → `|`; `\mathrm{e}` → `e`; a Unicode minus →
      `-`; decimals to exact fractions (`0.69` → `\frac{69}{100}`; antlr would make a 15-digit
      float). Then every remaining command must be in the subset (04 §4.3, plus `\cdot`,
      `\times` and Greek letters as variables), and a bare `\log` is refused: **antlr reads an
      unknown command as a symbol of that name** (`\approx 0.69` → `approx·0.69`) and a bare
      `\log` as `\ln`, so without the allowlist an answer outside the subset would "parse";
   2. splits a top-level comma-separated list itself. Brackets depend on the answer type
      (07 §7.3), which `answer(label)` passes on from `_answers.json`: with the `set` type,
      `(a, b)`, `[a, b)`, … are parsed as `sp.Interval`; with any other type, `(a, b)` is a
      tuple, i.e. a point such as a critical point `(1, -2)`. Each element goes to
      `sympy.parsing.latex.parse_latex(s, backend="antlr", strict=True)`. With the default
      `strict=False`, the parser silently drops everything after the first comma;
   3. post-processes the result. The antlr parser returns `\pi` and `e` as free symbols, so
      `pi`/`E`/`e` are replaced by `sp.pi`/`sp.E`, and `\infty` by `sp.oo`. It calls
      `.doit()` (`\frac{1}{2}` otherwise stays an unevaluated `Pow(2, -1)`), and replaces
      every other free symbol by the `mathcheck` symbol of the same name (`x`, `t`, … are
      real, `n` is an integer). Otherwise a correct `2x` would not equal the test's `2*x`. A
      multi-letter name is an error (the allowlist's backstop), and so is an equation
      (`x = 2`: the answer is the value), or a `C` outside the `antiderivative` type.

   It returns a SymPy expression, a tuple (for lists and points) or a set (`set`: an
   `Interval`, a `FiniteSet` for numbers, their `Union` for a list). With `antiderivative`,
   the answer must end in `+ C`, which is stripped (compare with `equal_up_to_constant`);
   with `numeric-<tol>` it must be a number; with `bool` it is `sp.true`/`sp.false`.
   `answer(label)` returns one value per math span, so a multi-part answer is a tuple of its
   parts. Its golden tests in `test_mathcheck.py` cover every item of 04 §4.3 and include
   `\frac{\pi}{4}`, `e^{2}`, `-2, 4` (two elements), `[0, 1)` (`set`), `(1, -2)` (a point,
   `expr`), `2x`, `\abs{x}`, `\log_{b}` and `+ C`; each expected value is written by hand as
   SymPy constructors, never produced by `parse_answer`. The traps above each have a test
   that shows the trap in the installed SymPy and that `parse_answer` handles it.
4. If the parser can't read an answer, the test **fails** with a message telling the author
   to rewrite the answer in the supported subset ([04 §4.3](04-notation-and-style.md)) or
   mark it `manual`.

Using MyST's own AST (rather than a second Markdown parser) means we read exactly what MyST
renders. The AST format is pinned with mystmd, and `test_mathcheck.py` contains an AST
fixture, so a format change shows up as one clear failing test on the upgrade PR.

### Equality helpers (and their pitfalls)

| Helper | Use for | How |
|---|---|---|
| `equal(a, b)` | closed-form values and identities; also tuples (elementwise), sets, True/False | `(a - b).is_zero`, then `simplify(a - b).is_zero`, then `(a - b).equals(0)`; if all are `None`, raise `Undecidable` (an `AssertionError`): **fail**, never silently pass. `nan`/`zoo` always fail. Two different symbols with one name (`sp.Symbol("x")` against mathcheck's real `x`) raise with a hint |
| `equal_up_to_constant(F, f, var, domain=None)` | antiderivatives `… + C` | `equal(diff(F, var), f)`, or `equal_on_domain` with a domain: $\frac{d}{dx}\ln\lvert x\rvert = \frac1x$ only for $x \ne 0$, so state it |
| `equal_on_domain(a, b, var, domain)` | identities valid only on a domain (e.g. $\sqrt{x^2} = x$ for $x \ge 0$) | the strongest assumption the domain gives (`positive`, `nonnegative`, `negative`, …), **and** a numeric spot check at 20 random points; both must agree |
| `numeric_spot_check(a, b, var, interval, n=50, tol=1e-9)` | an extra guard for any symbolic check, and the only check for numerical-method examples | mpmath at 30 digits, relative tolerance; points where a side is undefined are skipped, but fewer than half usable points fail |
| `limit_is(expr, var, point, value, dir="+-")` | limits, incl. one-sided and $\pm\infty$ | `sp.limit` decides, and a table of values at $10^{-3} \dots 10^{-12}$ from the point (or $\pm 10^{3} \dots 10^{12}$), 60 digits, must settle towards it; if they disagree, fail |
| `series_converges_to(term, n, value, start=1)` | series sums | `sp.summation`, cross-checked by partial sums to $10^4$; only when SymPy finds no closed form do the partial sums decide, with a tolerance |
| `solves_ode(y, ode)` | ODE solutions | `sp.checkodesol` |

Each helper returns True or False (False: decided to be false) and raises when it can't
decide, so tests write `assert equal(…)`. `mathcheck` wraps them to count each True result
as one assertion for the running test.

**Policy: a verification test reproduces each displayed step, not just the final answer.**
Most textbook errors are in intermediate lines. "Each displayed equality or inequality in a
worked example is either asserted in the test or annotated in the test as `# prose step,
reviewed manually`."

### What is *not* checked by code
- Proofs (see the checklist in §6.3).
- Graph sketches and qualitative claims ("$f$ is concave up on…"). These *can* often be
  checked (the sign of $f''$ on an interval via `sp.solveset`). Do so when cheap.
- Wording and pedagogy.

### Independence

When AI agents write content, the **verification test is written by a different agent run**
from the one that wrote the page. That run gets the page's statements but *not* the
solutions, and derives expected values independently ([10](10-ai-agents.md)). A test that
just copies the page's numbers verifies nothing.

## 6.2 Widget verification

Each widget that computes something (the δ in `epsilon-delta`, Riemann sums, Taylor
coefficients, Newton iterates) keeps those computations in a pure module in `widgets/_lib/`,
separate from rendering and with no JSXGraph import ([05 §5.8](05-tooling-and-build.md)).
`widgets/_tests/*.test.mjs` checks them against values that SymPy precomputed and committed
as JSON fixtures: `uv run python widgets/_tests/make_fixtures.py` writes them, and a test in
`tests/test_widget_checks.py` fails if the committed JSON differs from what the script writes
now, so nobody types an expected value. The
fixtures include the table of values of every `function-plot` figure on the site, so a new
figure's table is checked automatically. `npm run test:widgets` runs them locally and in CI
(in the `verify` job).

## 6.3 Proof review checklist

This is used by the human reviewer and by the AI reviewer agent. It is copied into the PR
template for topic PRs.

**Statements**
- [ ] Every hypothesis is stated, and the statement is false without each one (a remark or the
      rigorous track gives a counterexample for the non-obvious ones).
- [ ] Domains are explicit: "for all $x$ in $I$", "$a < b$", "$f$ continuous on $[a,b]$ and
      differentiable on $(a,b)$".
- [ ] Quantifier order is correct ($\forall \eps\, \exists \delta$, not $\exists \delta\, \forall \eps$).
- [ ] The statement matches the standard literature version, or the difference is remarked on.

**Proofs**
- [ ] The strategy is stated in the first sentence.
- [ ] Every hypothesis is used (an unused one means either the statement is weaker than it
      could be, or the proof is wrong).
- [ ] Every cited result is on the same page earlier, or in the page's prerequisite closure
      (also checked by CI's forward-reference check). On the same page, a proof may cite
      only results stated before the result it proves (02 §2.5).
- [ ] **No circularity**. Known traps in calculus:
      - $\lim_{x\to 0} \frac{\sin x}{x} = 1$ must not use L'Hôpital or $(\sin x)' = \cos x$
        (the derivative of sine is derived *from* this limit). Use the geometric squeeze argument.
      - The derivative of $e^x$ must follow from how $e$ / $\exp$ was *defined* on the
        preliminaries page. That definition choice is fixed in 08 and must be used consistently.
      - The MVT proof uses Rolle, which uses the EVT and Fermat. None of them may use the MVT.
      - Taylor's theorem must not assume the Taylor series converges.
- [ ] Edge cases: division by zero, $h \to 0$ with $h$ negative, $\Delta u = 0$ in the chain
      rule (the classic flawed proof), endpoints of intervals, empty sets.
- [ ] Inequalities: the direction is preserved when multiplying (sign of the factor stated).
- [ ] "Choose $\delta = \min(\dots)$" proofs: verify the final inequality chain with that δ.
- [ ] The proof matches its declared policy (F/R/S/D in 08).

**Examples and exercises**
- [ ] Each step is covered by a verification test or annotated as reviewed prose.
- [ ] The answer is in simplest conventional form (rationalised denominators, $\ln$ combined).
- [ ] The difficulty tier fits ([07](07-exercises.md)).
- [ ] The solution uses only methods available at this point in the graph.

**Pedagogy**
- [ ] Intuition comes before formalism; at least one picture or widget per main concept.
- [ ] Common mistakes reflect real student errors.
- [ ] Notation follows [04](04-notation-and-style.md) (`check_all.py` lints the mechanical part:
      bare `\log`, `\sin^{-1}`, raw `dx` in integrals, `]a, b[`, `\mathrm{e}`, degrees,
      "clearly"/"obviously"; 04 §4.4).

Each check runs in the CI job (and npm script) shown, so local and CI runs match
([05 §5.5](05-tooling-and-build.md)).

> No separate KaTeX check. The plan had `scripts/check_katex.mjs`, on the assumption that a
> KaTeX failure shows only as red text on the page. Stage 4 tested it ([05 §5.3](05-tooling-and-build.md)):
> mystmd renders every formula with its bundled KaTeX at build time, and an unknown macro, an
> unsupported command, a project macro missing an argument and an unclosed `\frac{1}{` are
> each a `⛔️` error, wherever the formula is, so the gated build fails. The `gate-katex-*`
> fixtures in `tests/` keep that true across mystmd upgrades. (Math in a front-matter `title`
> or `description` is not rendered at all, so no KaTeX check could see it there.)
>
> All scripts that scan content (`check_*`, `graph.py`, the plugin's `{where-this-leads}`)
> take the page list from the toc in `content/myst.yml`, not from a glob. A glob over
> `content/**/*.md` would also pick up the stale page copies that every build writes into
> `content/_build/`. The one exception is `check_toc.py`, which must compare the files on
> disk with the toc. Its glob excludes `_build/` and `_generated/`.

All `check_*` scripts print `file:line: message` (and GitHub `::error` annotations in CI)
so failures are clickable.

## 6.5 Review workflow per PR

1. Author (human or agent) opens a PR for **one topic** ([10](10-ai-agents.md)).
2. CI must be green.
3. The **AI reviewer agent** runs the checklist in §6.3 adversarially and posts findings.
4. The **owner** reviews the mathematics, at least the statements, proofs and a sample of
   solutions, and approves.
5. The status in front matter is updated **in the same PR** that earns it (see the next section).

## 6.6 Content status: draft → reviewed → verified

| Status | Meaning | Machine-checked preconditions | Human preconditions | Rendered as |
|---|---|---|---|---|
| `draft` | Written, may contain errors | builds, schema-valid | – | yellow "Draft — may contain errors" banner |
| `reviewed` | Mathematics read and approved by the owner | `reviewed_by` non-empty; `verify` file exists; ≥ 50 % of examples/exercises covered (§6.1: passing tests, not stubs); every prerequisite page exists and is ≥ `reviewed` | proof checklist completed in the PR | no banner; small "reviewed" badge |
| `verified` | Every computational claim machine-checked; proofs reviewed twice | **100 %** coverage of `eg-*` and `exr-*` labels (an exercise with a `manual` Answer: the reviewer's note); every prerequisite page ≥ `reviewed`; no forward-reference warnings (`check_labels.py` reports them as errors on verified pages); KaTeX clean (the build gate) | checklist completed by owner **and** reviewer agent | "verified" badge with a link to the test file on GitHub |

- **Where each precondition is checked.** `check_frontmatter.py` (`checks`): `reviewed_by`,
  the `verify` file, the prerequisite gate, the reviewer's notes. `check_coverage.py`
  (`verify`, after pytest): the 50 % and 100 % thresholds. `check_labels.py --forward-refs`
  (`checks`): forward references, errors on verified pages. The build gate (`build`): KaTeX.
- **The reviewer's note for `manual` answers.** A proof or a sketch has no machine-readable
  answer, so no test can cover its exercise. It counts as covered only when a reviewer, not
  the author or the verifier, records that they checked it, in the page's front matter:

  ```yaml
  maths:
    reviewed_by: [vronnblom]
    manual_checked:
      exr-calc-limit-eps-delta-linear: vronnblom   # exercise label: the reviewer who checked it
  ```

  `check_frontmatter.py` requires every key to be an exercise on the page whose Answer is
  `manual` (a computable answer needs a test, an example always does) and every value to be
  a handle in `reviewed_by`, which only the owner sets; `check_coverage.py` counts only such
  notes. Like `reviewed_by`, authors never add it (CLAUDE.md). It is a line in the front
  matter, so it shows in the diff the owner approves, and the edit guard below protects the
  page after it is verified. A test may still check the manual exercise's key claims (the
  template does); that test simply doesn't count towards coverage.
- Pages are published at every status (the banner tells readers), so drafts get eyes early.
- Any **edit to the mathematics** of a verified page (statement, proof, example, answer) sets
  it back to `reviewed` unless the PR re-establishes the verified preconditions. CI
  enforces this on pull requests with `check_verified_edits.py`, in its own workflow
  `guard.yml` (05 §5.7). It diffs the PR against its base commit (the job checks out the
  full history), and fails if a block inside a page that was verified at the base changed,
  was added or was removed while that page's verify file did not change. A block is every
  labelled directive or equation (an exercise includes its Answer) and every unlabelled
  proof, keyed by the statement it follows; prose outside blocks is not guarded. A renamed
  page is still compared with its old version. The failure asks for the status to be lowered
  (in the same PR) or the test to be updated. A typo-only PR can add the `typo-only` label, which the script reads from the
  event. `guard.yml` re-runs on `labeled`/`unlabeled`, so adding the label turns the check
  green without a new push; it is the only workflow that runs on label changes, so labelling
  a PR does not re-run the full CI. The guard runs only on pull requests, never on `main`.
- `content/about/status.md` shows the dashboard (pages per status per chapter). It includes
  a table that `scripts/generate.py` regenerates before every build
  ([05 §5.7](05-tooling-and-build.md), "Generated content").

## 6.7 Keeping `labels.lock` complete

`labels.lock` lists every label ever merged, so that a published label can't silently
disappear ([02 §2.4](02-information-architecture.md)). New labels must get into it, or the lock
protects nothing:
- `check_labels.py` **fails** if a label in the content is missing from `labels.lock`;
- `uv run python scripts/check_labels.py --update-lock` appends the missing labels (sorted,
  with the page they live on) and updates the page of a label that moved. Authors run it as a
  step of "how to add a topic" (CLAUDE.md) and commit the result with the page;
- a removed label needs a tombstone line in the lock (`label → replacement or reason`);
  otherwise the check fails. `--update-lock` never deletes a line, and a tombstoned label can't
  come back into the content.

The format is one label per line, `<label>  <page relative to content/>`, sorted, with `#`
